# План реализации сайта-портфолио

> **Для агента (Claude Code на Mac владельца).** Код в этом плане не приводится — только решения и проверки; реализацию пиши сам по требованиям и стеку.
>
> **Правила работы:**
> 1. Этапы — строго по порядку, шаги — по одному. После каждого шага выполни его тест; не переходи к следующему шагу, пока тест не пройден.
> 2. **Этот файл можно менять только одним способом — ставить галочку `- [x]` у выполненного шага.** Текст шагов, тесты, порядок и нумерацию не менять. Если план кажется неверным или неполным — остановись и спроси владельца.
> 3. **После каждого этапа — обязательная остановка.** Следующий этап не начинать, пока владелец не проверил текущий и явно не подтвердил (см. «Стандартное завершение этапа»).
> 4. **Два типа тестов.** *Автоматические* — команды, проверка файлов и HTML в `dist/`: выполняешь сам. *Визуальные* — внешний вид, клики, поведение в браузере, эмуляция в DevTools: их выполняет владелец в браузере или поручает тебе через Playwright. Сам Playwright без просьбы владельца не запускай. Шаг с визуальным тестом отмечай `[x]` только после подтверждения владельца.

**Цель:** статический сайт-портфолио Product Manager: главная с hero, карточками кейсов и футером + отдельная страница для каждого кейса.

**Архитектура:** Astro 6 собирает статический HTML. Кейсы — Markdown-файлы в коллекции `cases` со схемой валидации; общие данные — в `site.ts`. Компоненты `.astro` только отображают данные и не содержат текстов кейсов.

**Стек:** Node 24 LTS, npm, Astro 6, TypeScript, обычный CSS, `@fontsource-variable`, `@astrojs/sitemap`, Яндекс Метрика.

**Документы:** `memory-bank/portfolio-site-requirements-document.md` (далее — «Требования», номера разделов в скобках) и `memory-bank/tech-stack.md` (далее — «Стек»). Перед началом работы прочитай оба целиком.

## Глобальные ограничения

Действуют для каждого шага:
- Проект — только в папке `Portfolio/site/`. CV, `CLAUDE.md` и папку `memory-bank/` не удалять и не перемещать.
- Node 24 LTS (минимум 22). Пакетный менеджер — npm.
- Зависимости — после этапа 2 ровно 5 пакетов: `astro`, `@astrojs/sitemap`, `@fontsource-variable/<шрифт, выбранный владельцем>`; dev — `@astrojs/check`, `typescript`. Версии точные, без `^`.
- Git уже настроен на Mac владельца: `user.name`, `user.email` и прочие глобальные настройки git не менять.
- Только компоненты `.astro`. Никаких React/Vue/Svelte, Tailwind, Sass, CSS Modules, UI-библиотек.
- Стили — обычный CSS: переменные и база в `src/styles/global.css`, остальное — scoped `<style>` в компонентах.
- Шрифт — локально, никаких запросов к Google Fonts и другим внешним CDN.
- Сайт полностью работает с отключённым JavaScript (кроме Метрики и анимации появления).
- Весь видимый текст — на русском.
- Тексты кейсов — только в `.md`, общие данные — только в `site.ts`. В компонентах нет захардкоженного контента.
- Необязательные поля кейса без данных не заполняются; метка `[Заглушка: дописать]` допустима только в теле кейса.

## Зона повышенного внимания

Ситуации, которые легко пропустить. Каждая проверяется в указанном шаге:
1. **Длинные русские слова и названия** (например, «Двухлетняя продуктовая стратегия для 6 розничных направлений») не должны вылезать за карточку на 360px → шаг 10.3.
2. **Кейс без обложки, без результатов, без роли/длительности** — вёрстка не ломается, нет пустых блоков и висящих разделителей «·» → шаги 5.5, 6.3, 7.4.
3. **Один кейс и двадцать кейсов** — нет сломанной сетки и ссылки «Следующий кейс» на самого себя → шаги 7.6, 10.2.
4. **Отключённый JavaScript** — весь контент виден, включая элементы с анимацией появления → шаг 9.3.
5. **Не заданы `SITE_URL` и `metrikaId`** (это текущее состояние проекта) — сборка проходит без ошибок и предупреждений, внешних скриптов нет → шаги 8.4, 8.6.

## Стандартное завершение этапа

Последний шаг каждого этапа ссылается на этот блок. Выполнить по порядку:
1. Запустить `npx astro check` и `npm run build` из `site/`. **Тест:** обе команды завершаются без ошибок и без предупреждений — исключений нет. Этапы выстроены так, что на их границах проект всегда в полностью рабочем состоянии.
2. Убедиться, что все автоматические тесты этапа пройдены и все временные правки из тестов откачены (`git status` не показывает лишних файлов).
3. **ОСТАНОВИТЬСЯ и отчитаться владельцу:** что сделано за этап; список визуальных тестов этапа, которые нужно проверить (с номерами шагов); как посмотреть результат (`npm run dev` из `site/` → `http://localhost:4321`). Следующий этап не начинать.
4. Ждать подтверждения владельца. Если он нашёл проблемы — исправить, повторить пункты 1–3 и снова ждать.
5. **После подтверждения:** отметить `[x]` оставшиеся шаги этапа; открыть `memory-bank/progress.md` и задокументировать для будущих разработчиков, что сделано: номер и название этапа, дата, что реализовано, принятые решения и почему, отклонения от плана, как проверить результат.
6. Добавить в `memory-bank/architecture.md` архитектурные пояснения: что делает каждый созданный или изменённый файл, почему он устроен именно так, что получает на вход и что отдаёт, с какими файлами связан.
7. Сделать git-коммит с сообщением вида «Этап N: <название>».
**Тест блока:** владелец подтвердил этап; `git status` показывает чистое рабочее дерево; в `progress.md` есть запись об этапе; в `architecture.md` описан каждый файл, созданный или изменённый в этапе.
