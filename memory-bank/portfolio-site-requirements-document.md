## 1. Цель и аудитория

**Цель сайта:** показать кейсы, над которыми работал продакт-менеджер, и результаты, к которым они привели. Кейсы бывают разного масштаба — от запуска продукта с нуля до небольшой фичи.

**Аудитория:** рекрутеры, нанимающие менеджеры, фаундеры. Они заходят по ссылке из CV или соцсетей и за 1–2 минуты должны понять: кто это, что он делал и какие цифры получил.

**Критерии успеха:**
- За первый экран посетитель видит имя, роль, фото и может открыть CV или написать в Telegram/LinkedIn.
- Результаты кейсов видны прямо на главной, без перехода внутрь.
- Любой кейс открывается в один клик и читается как история.
- Владелец может переписывать тексты и менять структуру кейсов, не трогая код вёрстки.

## 2. Объём работ

**Входит:**
- Главная страница (hero, список кейсов, футер).
- Шаблон страницы кейса.
- Контент-модель кейсов в Markdown-файлах.
- Заглушки контента на основе CV (раздел 10).
- Адаптивная вёрстка, базовое SEO, Яндекс Метрика.
- Локальный запуск и сборка статического сайта.

**Не входит (не делать):**
- CMS и админка.
- Мультиязычность — сайт только на русском.
- Тёмная тема.
- Блог, форма обратной связи, комментарии.
- Фильтры и теги на главной.
- Закрытые кейсы и доступ по паролю — NDA-кейсов нет.
- Деплой на хостинг — пока только локально, но сборка должна позволять разместить сайт на любом статическом хостинге без доработок.

## 3. Ключевые технические решения

### 3.1. Контент без CMS
Тексты кейсов во время разработки будут переписываться много раз (подбирается лучшая логика повествования), а после запуска меняться не будут. Поэтому CMS не нужна. Решение:

- **Каждый кейс — отдельный Markdown-файл:** метаданные во frontmatter + свободный текст с картинками в теле.
- **Общие данные сайта** (имя, описание, контакты) — в одном конфиг-файле.
- **Вёрстка полностью отделена от контента.** Чтобы изменить текст, порядок секций или добавить/удалить кейс, достаточно отредактировать или создать файл — компоненты не трогаются.

### 3.2. Стек
- **Node.js 24 LTS** (минимум 22 — требование Astro 6). Версия фиксируется в `site/.nvmrc`, в `package.json` — `"engines": { "node": ">=22" }`.
- **npm** как пакетный менеджер: `save-exact=true` в `site/.npmrc` (версии без `^`), `package-lock.json` коммитится, чистая установка — `npm ci`.
- **Зависимости — строго этот список:** `astro`, `@astrojs/sitemap`, `@fontsource-variable/<шрифт>`; dev — `@astrojs/check`, `typescript`. Новый пакет добавляется, только если без него требование не закрывается.
- **Astro 6.x** (статическая генерация) + **Content Layer API**:
  - конфиг коллекций — `src/content.config.ts` (не `src/content/config.ts`);
  - коллекция `cases` с `loader: glob({ pattern: '**/*.md', base: './src/content/cases' })`;
  - схема через `z` из `astro/zod`, картинки — через хелпер `image()` в схеме;
  - идентификатор записи — `entry.id` (имя файла без расширения), `entry.slug` в Astro 6 нет;
  - рендер тела — функция `render()` из `astro:content`.
- Если обязательное поле кейса не заполнено, сборка должна падать с понятной ошибкой (это даёт схема).
- **Стили — обычный CSS:** `src/styles/global.css` (сброс, CSS-переменные цветов/шрифта/отступов, базовая типографика) + scoped `<style>` внутри компонентов `.astro`. Без Tailwind, Sass, CSS Modules и UI-библиотек.
- **UI-фреймворки (React, Vue, Svelte) не использовать** — только компоненты `.astro`.
- JavaScript на клиенте — минимум: сайт должен работать и с отключённым JS (кроме Метрики).
- Картинки — через `astro:assets`: ресайз, WebP/AVIF, lazy-loading (обложка первой карточки — `loading="eager"`). `sharp` ставится вместе с Astro; если сборка ругается на sharp — добавить его явно: `npm i -E sharp`.
- Подписи к картинкам в Markdown — **свой rehype-плагин без внешних пакетов** в `src/lib/rehype-figure.mjs` (~20 строк, обход дерева рекурсией): абзац с `<img title>` → `<figure>` + `<img>` + `<figcaption>`. Из коробки Astro этого не делает.
- URL сайта (`site` в `astro.config`) берётся из переменной окружения `SITE_URL`. Домена пока нет, поэтому переменная может быть не задана (см. раздел 9).

### 3.3. Расположение и структура проекта
- Проект Astro создаётся в **подпапке `site/`** папки Portfolio. В корне Portfolio лежат CV (PDF), `CLAUDE.md` и папка `memory-bank/` (этот документ, `tech-stack.md`, `implementation-plan.md`, `architecture.md`, `progress.md`) — их **не удалять и не перемещать**.

### 3.4. Команды
Все команды выполняются из папки `site/`.
```bash
npm ci             # чистая установка по lockfile (при самом первом создании проекта — npm install)
npm run dev        # локальный сервер с hot reload, http://localhost:4321
npm run build      # статическая сборка в dist/
npm run preview    # просмотр сборки, http://localhost:4321
npx astro check    # проверка типов и схемы контента
```
Lighthouse: запустить `npm run build && npm run preview`, затем `npx lighthouse http://localhost:4321 --preset=desktop` и без `--preset` для мобильной оценки (или вкладка Lighthouse в Chrome DevTools).

## 4. Карта сайта

| Страница | URL | Назначение |

## 5. Главная страница

Блоки сверху вниз: **Hero → Кейсы → Футер**. Отдельного меню навигации нет.

### 5.1. Hero
| Элемент | Требования |
|---|---|
| Имя | Крупная типографика — главный визуальный акцент экрана. |
| Роль | «Product Manager». |
| Фото | Портрет. Пока фото нет — нейтральный плейсхолдер того же размера и пропорций. |
| Краткое описание | 2–4 предложения о себе (из конфига). |
| Кнопка «CV» | Открывает `/cv.pdf` в новой вкладке. |
| Кнопка «LinkedIn» | Внешняя ссылка, новая вкладка. |
| Кнопка «Telegram» | Ссылка `https://t.me/<telegram>`, новая вкладка. |

- На десктопе: текст и кнопки слева, фото справа (или наоборот — на усмотрение дизайна, главное — баланс).
- На мобильных: всё в одну колонку, кнопки доступны без скролла, если позволяет высота экрана.

### 5.2. Список кейсов
- Секция с `id="cases"` (на неё ведёт ссылка «← Все кейсы»), заголовок, например «Кейсы».
- **Раскладка: одна широкая карточка в ряд** (кейсы идут друг под другом).
- Поддержка **от 1 до 20 карточек** без пагинации и без поломки вёрстки.
- Порядок — по полю `order` (по возрастанию). Кейсы с `draft: true` не показываются и не генерируются.

**Карточка кейса:**
| Элемент | Источник | Требования |
|---|---|---|
| Визуал | `cover` | Обложка/макет. На десктопе занимает ~55–60% ширины карточки. |
| Название | `title` | Из названия должно быть понятно, это продукт с нуля или фича — отдельных тегов типа нет. |
| Компания и год | `company`, `year` | Мелкая строка метаданных, например «Банк Санкт-Петербург · 2025». |
| Краткое описание | `summary` | 1–2 предложения. |
| Результаты | `results` | Первые 1–3 метрики: крупно `value` + мелко `label` (например, **+12%** конверсия в выдачу карты). |
| Ссылка | — | «Посмотреть кейс →». **Кликабельна вся карточка**, а не только ссылка. |

- Десктоп (≥1024px): текст слева, визуал справа.
- Планшет и мобильные (<1024px): визуал сверху, текст под ним.
- Ховер: лёгкий отклик (сдвиг/тень/масштаб картинки), без резких анимаций.
- Если `results` пусто — блок результатов скрывается, карточка не ломается.
- Если `cover` нет — нейтральный плейсхолдер с названием компании.

### 5.3. Футер
Используется на всех страницах.
- Имя (повтор).
- Город.
- Email (ссылка `mailto:`).
- Телефон (ссылка `tel:`) — выводится, только если заполнен в конфиге.
- Telegram (отображается как `@<telegram>`), LinkedIn.
- Строка © с текущим годом.

## 6. Страница кейса

Состоит из двух частей: **фиксированная шапка** (одинаковая структура для всех кейсов, данные из frontmatter) и **гибкое тело** (Markdown — набор и порядок секций свободный).

### 6.1. Верхняя панель
- Ссылка «← Все кейсы» → `/#cases`.
- Имя владельца — ссылка на главную.

### 6.2. Фиксированная шапка
| Элемент | Источник |
|---|---|
| Название | `title` |
| Краткое описание | `summary` |
| Мета: компания · год · роль · длительность | `company`, `year`, `role`, `duration` (роль и длительность — только если заданы) |
| Ключевые метрики | `results` — все (до 4), в ряд крупными цифрами |
| Обложка | `cover` — широкое изображение |

### 6.3. Гибкое тело
- Рендерится из Markdown-тела файла кейса.
- **Рекомендуемая структура по умолчанию** (используется в заглушках; владелец может переставлять, удалять и добавлять секции):
  1. Контекст
  2. Проблема
  3. Цели
  4. Решение
  5. Результаты
- Поддерживаемые элементы: заголовки `##` / `###`, абзацы, списки, жирный/курсив, цитаты, ссылки, картинки.
- **Картинки в теле:** выходят шире текстовой колонки (текст ~680–720px, картинки до ~1100px). Подпись — из `title` картинки, выводится как `<figcaption>` под ней (см. 3.2). Без `title` — картинка без подписи.

### 6.4. Низ страницы
- Блок «Следующий кейс» — название и ссылка на следующий по `order` опубликованный кейс (после последнего — на первый). **Если опубликован только один кейс — блок не выводится.**
- Футер (как на главной).

## 7. Модель данных

### 7.1. Конфиг сайта (`site/src/config/site.ts`)
Значения — в разделе 10.
| Поле | Тип | Обязательно | Формат |
|---|---|---|---|
| `name` | string | да | Имя и фамилия |
| `role` | string | да | Роль для hero |
| `about` | string | да | 2–4 предложения для hero |
| `photo` | image | нет | Путь в `src/assets/profile/` |
| `city` | string | да | Город |
| `email` | string | да | Адрес почты |
| `phone` | string | нет | Телефон в человекочитаемом виде; для `tel:` убрать всё, кроме цифр и `+` |
| `telegram` | string | да | Ник **без `@`** |
| `linkedin` | url | да | Полный URL профиля |
| `cvPath` | string | да | `/cv.pdf` |
| `metrikaId` | string | нет | ID счётчика Яндекс Метрики |
| `seoDescription` | string | да | Описание для meta / OG главной |

### 7.2. Кейс (frontmatter в `site/src/content/cases/<slug>.md`)
| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `title` | string | да | Название кейса |
| `summary` | string | да | 1–2 предложения для карточки и шапки |
| `company` | string | да | Компания |
| `year` | string | да | Год или период: «2025», «2022–2024» |
| `role` | string | нет | Роль в кейсе |
| `duration` | string | нет | Длительность: «4 месяца» |
| `results` | список `{ value: string, label: string }` | нет, до 4 | `value` — короткая цифра («+12%», «×2», «до −30%», «10+»), `label` — что изменилось. На карточке — первые 3, в шапке — все |
| `cover` | `image()` | нет | Обложка, путь относительно .md файла |
| `coverAlt` | string | если есть `cover` | Альт-текст обложки |
| `order` | number | да | Порядок на главной |
| `draft` | boolean | нет, по умолч. `false` | Скрыть кейс |

**Необязательные поля без данных не заполнять** (не ставить туда заглушки) — иначе пустышка окажется в шапке кейса.

### 8.1. Референсы
| Сайт | Что взять |

### 8.2. Принципы
- Минимализм, светлая тема, много воздуха.
- Акцент на макетах и цифрах результатов — это главное содержимое.
- Нейтральная палитра + один акцентный цвет. Цвета задаются CSS-переменными в одном месте.
- **Шрифт и акцентный цвет выбирает владелец** на этапе 2 из 3 вариантов, которые предложит агент (первый — на усмотрение агента). Шрифт — один variable-шрифт без засечек с кириллицей из fontsource (например, Onest, Manrope, Golos Text), подключённый **локально** через `@fontsource-variable/*`. Google Fonts и внешние CDN не использовать.
- Цифры результатов — крупно и контрастно, подписи — мелко и спокойно.
- Анимации сдержанные (появление при скролле, ховер карточек) и отключаются при `prefers-reduced-motion`.

## 9. Нефункциональные требования

**Адаптивность:** корректное отображение от 360px до 1920px+. Контрольные ширины: 360, 768, 1024, 1440. Нет горизонтального скролла.

**Производительность:** Lighthouse Performance ≥ 90 на мобильных для главной (как запускать — 3.4). Картинки оптимизированы, ниже первого экрана — lazy-loading.

**SEO:**
- Уникальные `<title>` и `meta description` для каждой страницы (для кейса — из `title` и `summary`).
- Open Graph: `og:title`, `og:description`, `og:image` (для кейса — обложка, для главной — фото или общая картинка).
- `lang="ru"`, favicon, `robots.txt` — статичный файл в `public/` (без пакета).
- Мета-теги и OG собираются в общем layout `src/layouts/Base.astro`, данные приходят пропсами.
- **Зависимость от `SITE_URL`:** `@astrojs/sitemap` и абсолютные URL в `og:image` требуют `site`. Если `SITE_URL` задан — генерируется карта сайта (`sitemap-index.xml` + `sitemap-0.xml` — так называет файлы `@astrojs/sitemap`), а OG-картинки получают абсолютные URL. Если не задан (локальная разработка) — sitemap не подключается, сборка проходит без ошибок и предупреждений.

**Доступность:** семантическая разметка (`header`, `main`, `article`, `footer`), alt у всех картинок, видимый фокус у ссылок и кнопок, достаточный контраст текста.

**Яндекс Метрика:**
- Официальный код счётчика — инлайн (`is:inline`) в `Base.astro`. Подключается, только если в конфиге задан `metrikaId`. Если не задан, скрипт не загружается.
- Цели кликов — через атрибуты `data-goal` и один делегированный обработчик клика.
- Цели (`reachGoal`) на клики: `cv_click`, `linkedin_click`, `telegram_click`, `email_click`.
- Цель `case_open` отправляется **при загрузке страницы кейса**, а не по клику на карточку: при клике браузер сразу уходит со страницы и запрос может потеряться.

**Внешние ссылки:** открываются в новой вкладке с `rel="noopener noreferrer"`.
