## 1. Критерии выбора

Взяты из требований и условий проекта:

1. **Контент отдельно от вёрстки.** Тексты кейсов будут переписываться много раз; новый кейс = новый `.md` файл без правки кода.
2. **Сборка падает на ошибке в данных.** Пропущенное обязательное поле или битый путь к картинке должны ловиться при сборке, а не на живом сайте.
3. **Статика.** Сайт не меняется после запуска, нет сервера, базы, авторизации. Готовая папка `dist/` кладётся на любой хостинг.
4. **Производительность.** Lighthouse ≥ 90 на мобильных: оптимизация картинок, минимум JS.
5. **Реализует и поддерживает AI-агент.** Стек должен быть популярным, хорошо документированным и однозначным — чтобы агент не угадывал.
6. **Надёжность во времени.** Минимум зависимостей, закреплённые версии, сайт должен собираться так же через год.

## 2. Почему Astro, а не что-то проще или сложнее

| Вариант | Простота | Надёжность | Покрывает требования | Вердикт |
|---|---|---|---|---|
| **Чистый HTML + CSS** | Максимальная, ноль зависимостей | Максимальная | **Нет.** Каждый кейс — копия HTML-разметки; правка структуры = правка 20 файлов. Нет валидации данных, оптимизацию картинок делать вручную. | Не подходит: ломает главное требование — контент отдельно от вёрстки |
| **Hugo** | Один бинарник, без npm | Очень высокая | Почти. Markdown, картинки, sitemap и подписи (render hooks) — из коробки. Но **нет схемы данных**: проверки полей пишутся вручную в шаблонах. Go-шаблоны многословны и неочевидны. | Сильная альтернатива, если важнее всего ноль npm-зависимостей |
| **Eleventy 3** | Высокая | Высокая | Частично. Нет встроенной валидации frontmatter и типизации; оптимизация картинок — отдельный плагин. | Проще Astro по устройству, но требования закрываются ручным кодом |
| **Astro 6** | Высокая: шаблоны — почти чистый HTML | Высокая при закреплённых версиях | **Полностью.** Схема контента с понятными ошибками, проверка путей к картинкам, оптимизация изображений, ноль JS по умолчанию. | **Рекомендуется** |
| **Next.js / Nuxt / SvelteKit** | Средняя | Средняя | Да, но с избытком: React/Vue-рантайм, гидрация, серверные режимы. | Избыточно для статичной витрины из 12 страниц |
| **Tilda / Framer / Webflow** | Максимальная для человека | Зависит от платформы | Нет: подписка, нет git-истории, AI-агент не может работать с кодом, вендор-лок. | Не подходит под формат «делает AI-агент» |

**Вывод:** Astro — самый простой вариант, который закрывает **все** требования встроенными средствами, без самописной валидации и обвязки. Всё, что проще (HTML, Eleventy, Hugo), требует дописывать руками то, что в Astro уже есть и проверено.

## 3. Решения по слоям

### 3.1. Рантайм и пакеты
- **Node.js 24 LTS** — актуальная LTS-ветка с самым долгим сроком поддержки; Astro 6 требует Node 22+, поэтому 22 LTS тоже допустим. Установка на Mac — через Homebrew (формула `node@24`). Версия фиксируется в `site/.nvmrc` и в `package.json` → `"engines": { "node": ">=22" }`.
- **npm**, а не pnpm/yarn/bun: ничего не нужно ставить дополнительно, меньше мест для сбоя.
- В `site/.npmrc`: `save-exact=true` — версии пакетов записываются точно, без `^`.
- `package-lock.json` коммитится. Чистая установка — `npm ci`.

### 3.2. Контент и валидация
- Content Layer API: `site/src/content.config.ts`, коллекция `cases` с `glob()`-loader.
- Схема на `z` из `astro/zod`, обложка — через `image()`: Astro сам проверит, что файл картинки существует.
- Конфиг сайта (`src/config/site.ts`) — обычный типизированный TS-объект. Отдельная коллекция для него не нужна.

### 3.3. Шаблоны и стили
- Только компоненты `.astro`. **Никаких UI-фреймворков** (React, Vue, Svelte): интерактивности на сайте нет, фреймворк добавил бы JS и зависимости без пользы.
- **Обычный CSS**, без Tailwind и препроцессоров:
  - `src/styles/global.css` — сброс, CSS-переменные (цвета, шрифт, отступы, брейкпоинты в комментариях), базовая типографика;
  - стили компонентов — в `<style>` внутри `.astro` (Astro делает их scoped автоматически).
  - Почему не Tailwind: ещё одна зависимость и своя система классов; для ~6 компонентов обычный CSS короче и читаемее.
- Ховер и появление при скролле — CSS (`transition`, `@media (prefers-reduced-motion)`). Для анимации появления допустим один небольшой инлайн-скрипт с `IntersectionObserver`; без него контент должен быть виден сразу.

### 3.4. Шрифт
- Один variable-шрифт без засечек с кириллицей из fontsource (например, **Onest**, **Manrope**, **Golos Text**) — через пакет `@fontsource-variable/<шрифт>`. Конкретный шрифт выбирает владелец на этапе 2 из 3 вариантов, предложенных агентом; пакеты невыбранных шрифтов удаляются.
- Почему локально, а не Google Fonts: нет внешнего запроса при загрузке (лучше для Lighthouse и приватности), нет зависимости от доступности сторонних CDN для посетителей из РФ.

### 3.5. Картинки
- `astro:assets`: компонент `<Image />` в шаблонах, а картинки из Markdown Astro оптимизирует сам. Форматы WebP/AVIF, `loading="lazy"` ниже первого экрана, обложку первой карточки — `loading="eager"`.
- `sharp` устанавливается вместе с Astro; если при сборке ошибка про sharp — добавить его явно (`npm i -E sharp`).

### 3.6. Подписи к картинкам
- Свой rehype-плагин в `site/src/lib/rehype-figure.mjs`: находит `<img>` с `title` внутри абзаца и заменяет абзац на `<figure><img><figcaption>`. ~20 строк, обход дерева — простой рекурсией, **без внешних пакетов**.
- Почему не готовый пакет: малопопулярные плагины часто заброшены; собственный код на 20 строк надёжнее лишней зависимости.

### 3.7. SEO и аналитика
- `@astrojs/sitemap` подключается в `astro.config.mjs` **только если задан `SITE_URL`** (условное добавление в массив `integrations`).
- Мета-теги и OG — в одном общем layout (`src/layouts/Base.astro`), данные передаются пропсами.
- `robots.txt` — статичный файл в `public/` (без пакета).
- Яндекс Метрика — официальный код счётчика, инлайн в layout через `is:inline`, обёрнут в условие `metrikaId`. Цели — `ym(id, 'reachGoal', ...)` через `data-goal` атрибуты и один делегированный обработчик клика.

### 3.8. Проверки качества
Отдельного тестового фреймворка не нужно: на сайте нет логики, которую стоило бы покрывать юнит-тестами.
- `npx astro check` — типы и схема контента;
- `npm run build` — сборка (падает на невалидных данных);
- Lighthouse — производительность и доступность;
- ручная проверка на контрольных ширинах 360 / 768 / 1024 / 1440.

```json
{
  "engines": { "node": ">=22" },
  "dependencies": {
    "astro": "6.x.x",
    "@astrojs/sitemap": "x.x.x",
    "@fontsource-variable/<выбранный-шрифт>": "x.x.x"

  "devDependencies": {
    "@astrojs/check": "x.x.x",
    "typescript": "x.x.x"
  }
}
```
Версии `x.x.x` — актуальные на момент установки, записываются точно (`save-exact`).

## 5. Чего сознательно нет

| Не используем | Почему |
|---|---|
| React / Vue / Svelte | Нет интерактивности — только лишний JS и зависимости |
| Tailwind, Sass, PostCSS-плагины | Обычный CSS с переменными покрывает всё |
| CMS (Decap, Sanity, Strapi и т. п.) | Контент правится в Markdown; после запуска не меняется |
| Google Fonts / внешние CDN | Шрифт локально через fontsource |
| ESLint / Prettier | Для сайта из ~10 файлов кода — лишняя настройка; `astro check` ловит реальные ошибки |
| Юнит-/e2e-тесты | Нет бизнес-логики; проверка = сборка + `astro check` + Lighthouse |
| Docker | Локальной Node достаточно; на хостинг уходит статическая папка |

## 6. Правила надёжности

1. **Версии закреплены:** `.nvmrc`, `save-exact`, `package-lock.json` в git, установка через `npm ci`.
2. **Мажорные обновления — только осознанно.** API Astro заметно менялся между мажорными версиями (4 → 5 → 6). После запуска сайт обновлять не нужно: собранный `dist/` — это просто HTML, CSS и картинки, он не «протухает».
3. **Минимум зависимостей:** каждый новый пакет — только если без него требование не закрывается.
4. **Одна точка правды для данных:** контент — в `.md`, общие данные — в `site.ts`, цвета и шрифты — в CSS-переменных.

## 7. Хостинг (когда понадобится)

Сборка — обычная статика, поэтому подходит любой статический хостинг: GitHub Pages, Netlify, Cloudflare Pages, Vercel, Яндекс Object Storage (статический сайт) или любой российский хостинг.
Основная аудитория — в РФ, поэтому перед выбором стоит **проверить доступность и скорость из России** на момент деплоя: у зарубежных платформ она бывает нестабильной. Самый предсказуемый вариант для российских посетителей — Яндекс Object Storage или российский хостинг.
